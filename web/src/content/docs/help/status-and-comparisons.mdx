<p class="lede">
  PopSub is young, small and honest about it. This page says where it stands, how it compares
  with tools you may know, and what it doesn't do yet.
</p>

## Where it stands

- **Version 0.x.** The protocol and client APIs can still change. The
  [changelog](https://github.com/soumyadepp/popsub/blob/main/CHANGELOG.md) lists every
  release.
- **One process.** It doesn't cluster or replicate, so one machine is the whole deployment.
- **Guarantees are written down.** What's promised, and what isn't, is in the
  [design doc](https://github.com/soumyadepp/popsub/blob/main/docs/DESIGN.md).

## Compared with other tools

| | Keeps history to replay | Acks per subscriber | More than one node | Browsers connect directly |
|---|---|---|---|---|
| **PopSub** | Yes | Yes | No | Yes |
| Redis pub/sub | No | No | Yes | No |
| NATS (core) | No | No | Yes | Yes |
| NATS JetStream | Yes | Yes | Yes | Yes |
| MQTT brokers | Latest value only | Yes | Some | Yes |
| Kafka | Yes | Per consumer group | Yes | No |

**Choose PopSub** when you want history, acknowledgements, accounts and per-topic
permissions in one small binary, with client libraries that handle reconnects for you.

**Choose something else** when you need:

- Replication or high throughput today: NATS JetStream or Kafka.
- Devices that only speak MQTT: Mosquitto or EMQX.
- Exactly-once delivery. PopSub delivers at least once, and every message carries its topic
  and `seq` so consumers can spot repeats.

## What's missing

From section 12 of the design doc, most important first.

### For small applications

1. Your own backend can't issue PopSub tokens. Tokens only come from PopSub's own login.
2. There's no HTTP publish, so a serverless function has to open a WebSocket.
3. There are no storage quotas per account, so one account can fill the disk.
4. Backups and upgrades aren't documented yet.

### For devices

5. No MQTT listener.
6. No "last will", so a dashboard can't learn a device dropped off.
7. No retained value that every new subscriber gets without asking.
8. Logging in again needs the password on the device.
9. JSON and base64 are expensive on metered links.

### For running it

10. Capacity hasn't been measured. Benchmarks are planned.
11. Power loss and consumers that never read aren't covered by tests yet.
12. A renewed TLS certificate needs a restart.
13. Metrics are pushed over OTLP. There's no Prometheus endpoint.
14. No `SECURITY.md`, and the frame parser isn't fuzzed.
15. No Swift, Kotlin, C or MicroPython client.

Where it's heading, clustering included, is in
[section 13 of the design doc](https://github.com/soumyadepp/popsub/blob/main/docs/DESIGN.md#13-proposed-direction).
